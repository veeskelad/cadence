# Continue on your Mac or PC

The landing changes are a normal change to this repository. The runtime patch is a
separate, unreleased change that still needs integration into the maintained Cadence
source. Do not patch a working installed release or replace a published ZIP.

## Give this task to your local coding agent

> Read this PR and patches/README.md. Find the existing Cadence source repository and
> the separate website/distribution checkout; verify their identities before editing.
> Preserve uncommitted work and create a new source branch/worktree. Inspect the source
> repository's instructions and release process. Run git apply --check on the runtime
> patch. If source layout or generated skill mirrors differ, stop automatic application
> and explain the mismatch; adapt the narrowly scoped fixes to their canonical source
> instead of forcing a patch onto generated files. Keep the three shipped skill mirrors
> consistent through the existing build process. Run the source repository's required
> tests, then the regression tests and first-result guide in a new temporary project.
> Report every passed/failed/blocked check and give the resulting MP4 for inspection.
> Do not alter existing user projects, merge, deploy, overwrite release 1.2, publish a
> new release, or change current/manifest.json without separate approval.

## Get the PR files safely

Use the existing website/distribution checkout or a fresh clone of
`https://github.com/veeskelad/cadence.git`. Fetch and check out the PR branch in a clean
worktree. Do not discard local changes or switch a dirty checkout blindly.

The review files are:
- `patches/cadence-1.2-runtime.patch`
- `patches/README.md`
- `tools/check-runtime-patch.py`
- `tests/install-prompt-smoke/`

Run the independent checks before touching maintained source:

```sh
node --test tests/*.test.mjs
python3 tests/install-prompt-smoke/test_install_prompt.py --archive 1.2/cadence-1.2.zip
python3 tools/check-runtime-patch.py 1.2/cadence-1.2.zip
```

In a clean source worktree, inspect the patch, then:

```sh
git apply --check /absolute/path/to/cadence-1.2-runtime.patch
```

Only after the check succeeds and the target files are confirmed to be canonical source:

```sh
git apply /absolute/path/to/cadence-1.2-runtime.patch
node --test engine/safe-build.test.mjs tests/startup.test.mjs
```

A failed check is a reason to review differences, not use force or unsafe-path options.
The public release patch cannot include source-only tests or build rules that were never
published; the local agent must also run those checks from the actual source instructions.

## First real video

Read `guides/FIRST-RESULT.md` in the patched source. Its shell examples are for Bash on
macOS/Linux/WSL. Native Windows still needs an end-to-end verification; do not paste Bash
commands into PowerShell and assume they are equivalent.

Check Node 22+, Python 3.11+, ffmpeg/ffprobe and the required Python packages. Install
missing dependencies only with consent. Start a **new uniquely named test project**, use
the demo beat, build, then run the package's check/render/deliver/check_reel steps. Do not
reuse a user's existing project or remove an old unmarked build folder to make a test pass.

The new work-root command resolves the location:

```sh
python3 scripts/cadence_paths.py work-root
```

Keep media generated by this test in that new project. Check frames and audio of the
finished MP4 before reporting the render as verified. Publication remains a separate step.
