# Связный набор мобильных состояний

## Платформа и сценарий

Выбрать целевую среду: конкретная нативная платформа либо нейтральная мобильная концепция. Сохранить навигацию реального приложения; если её нет, описать простую систему по задаче. Не смешивать особенности разных платформ без причины. Точная системная геометрия неизвестна — записать допущение, не объявлять концепт официальным компонентом.

Строить путь из действий и переносимого состояния:

```text
screen_id:
user_goal:
state_before:
visible_content_and_source:
primary_action:
state_after:
next_screen_or_exit:
navigation_back:
platform_and_system_regions:
shared_contract:
output_format:
acceptance:
```

У перехода есть причина. Выбранный товар, заметка или настройка не исчезает на следующем экране. Для onboarding показывать разные полезные понятия, а не одинаковую картинку с новым лозунгом. Recovery/permission/error нужны, когда входят в реальный запрос; не добавлять все возможные экраны.

## Семейства задач

Деньги/операции: сумма, единица, адресат, статус и действие различимы; без выдуманной аналитики. Здоровье/прогресс: источник и период показателя известны, мотивация не заменяет данные. Планирование: приоритет задач и действия не спрятаны декором. Общение: отличаются создание, просмотр, профиль и приватность. Каталог: товар → детали → выбор → итог с сохранением варианта. Медиа: обложка/название/действие не уступают рамке устройства. Эти предпочтения не являются фиксированными шаблонами.

## Система вида

Зафиксировать: платформу, палитру, роли текста, интервалы, радиусы, иконографику, медиа-ratios, model устройства/масштаб и навигацию. Экран может быть насыщенным, если каждая зона читается и имеет функцию. Воздух отделяет действия; не заполнять его декоративной статистикой. Кегль не уменьшать ради лишней панели.

Материал выбирать по смыслу: список для выбора, профиль для идентичности, изображение для товара, сообщения для общения. Иконки одной системы веса/заливки; доступная библиотека не требует смены ради моды. Декор и texture не должны конкурировать с содержимым. Под текстом на фото сделать локальное затихание фона/подложку; важный продукт остаётся узнаваемым.

Различать content area, status/app bar, navigation, indicator/gesture regions и sheet region. Содержимое не накладывается на системные зоны. Для настоящего приложения контролировать hit targets и чтение на устройстве; изображение не проверяет usability.

## Устройство и серия

Phone frame использовать, когда он помогает контексту; raw screen — когда важна детализация или пользователь просит его. Держать один масштаб/обводку/свет и общие gutters серии. Не делать рамку главным объектом. Во внешнем 9:16 кадре важный экран и текст внутри x0.06W…0.82W/y0.15H…0.75H; внутренние системные поля телефона остаются отдельными.

Каждый нужный экран дать читаемым самостоятельным листом. Общая схема пути может существовать рядом; она не заменяет детали. При неясной надписи не угадывать: использовать входной текст. Дополнительный лист нужен для конкретной неразличимой области, а не обязательной квоты. Brief содержит экран, состояние, точные строки, assets, geometry, системные зоны и неизменные правила серии.

## Приёмка

Пройти путь: откуда экран появился, какое действие доступно, что меняется, как вернуться. Сверить состояние между листами, сетку/глифы/контраст и единый бренд. Для концепта явно указать условность данных. Не выдавать рисунок за работающую навигацию. Для видео проверить роль экрана в сцене, UI-overlay площадки, cover crops и параметры итогового файла.
